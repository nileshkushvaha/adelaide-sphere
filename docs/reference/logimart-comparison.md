# Logimart reference comparison

**Purpose.** The client authorised a read-only inspection of `/Users/nileshkushvaha/Sites/laravel/logimart` (Laravel 12 + Filament 4 + Spatie Permission/Settings/Activitylog) because it already ships the same *kinds* of administration modules Melbourne Sphere is now adding. This document records what that project actually does, what is worth adopting, what must change for Melbourne Sphere, and what must **not** be copied.

**Inspection boundary honoured.** Read-only file reads only. No Logimart service was started, no migration run, no database touched, no `.env` or secret read or printed, no Laravel/PHP code copied into this repository, and no Logimart customer or production data was accessed. Everything below is a behavioural observation from source, cited by path so a reviewer can confirm it.

**Standing rule.** Logimart is a *user-experience and completeness* reference, not a security or architecture reference. Its implementation is assumed insecure until proven otherwise; several concrete weaknesses are recorded in §13. Melbourne Sphere's own SRS governs every decision — where the two disagree, the SRS wins.

## 1 Shared settings architecture

| | |
| --- | --- |
| **Logimart behaviour** | Thirteen typed settings classes under `app/Settings/*.php` (Spatie Laravel Settings), each a plain property bag with a `group()` key: `GeneralSettings`, `MailSettings`, `SeoSettings`, `AuthenticationSettings`, `PasswordPolicySettings`, `LoginSecuritySettings`, `SessionSettings`, `AccountProtectionSettings`, `RegistrationSettings`, `SocialSettings`, `TrackingSettings`, `WhatsAppSettings`, `FormSettings`. One Filament page per group (`app/Filament/Pages/Settings/*`, `app/Filament/Pages/Security/*`), each gated by a shared `HasSecurityAccess` / `HasSettingsAccess` trait that maps the page to a single permission. Audit is a shared trait, `LogsSettingsUpdates`, that snapshots before/after and records only changed fields, with an explicit allowlist of financial/personal fields recorded as presence-only. |
| **Suitable for Melbourne Sphere** | Typed setting groups instead of one untyped key-value table; one owning permission per group; a shared change-audit helper that diffs and records only what changed; recording *presence* rather than value for sensitive fields; "an unchanged save logs nothing". |
| **Must change** | Settings must be validated **server-side by an explicit schema** and go through the API envelope with `expectedVersion`, not a UI form object. Melbourne Sphere already has `settings/general-settings.ts` as the pattern to extend (typed key, validator, version, audit) — the new groups join that model rather than introducing a second one. Each setting also needs the metadata Logimart does not carry: data type, default, public/private visibility, runtime-changeable vs restart-required, sensitive flag, required permission, and cache-invalidation consequence. |
| **Do not copy** | `MailSettings` stores an SMTP **password** in the settings table (encrypted at rest, but still readable by the settings API and editable in a browser form). Melbourne Sphere keeps every credential — the Resend API key included — in environment-managed secrets, never in a settings table and never in an API response (SEC 004). Spatie's lazy-hydration property bag and its `group()` convention are Laravel-specific and are not reproduced. |
| **Governing SRS** | SET 001–005 (new), CFG 001, SEC 004, API 005, RBAC 002/006/012. |

## 2 Resend provider and Email Logs

| | |
| --- | --- |
| **Logimart behaviour** | `app/Services/Mail/EmailLogService.php` listens to framework mail/notification events (`NotificationSending`, `MessageSending`, `MessageSent`, `NotificationFailed`, `NotificationSent`) and writes an `email_logs` row keyed by the notification id. It stamps an `X-App-Email-Log-Id` header and a `Resend-Idempotency-Key` header on the outgoing message, and stores the provider message id from `X-Resend-Email-ID`. The table (`2026_07_07_000000_create_email_logs_table`) carries id, notification id/type, category, provider, mailer, status, subject, from address/name, `to`/`cc`/`bcc` JSON, queued flag, unique provider message id, error text, attempts, metadata JSON and `sent_at`/`delivered_at`/`failed_at`. The Filament resource (`app/Filament/Resources/EmailLogs/EmailLogResource.php`) is strictly read-only — `canCreate`/`canEdit`/`canDelete`/`canDeleteAny` all return `false` — with status/category/provider filters, a searchable subject and provider message id, a detail infolist and no bulk actions. |
| **Suitable for Melbourne Sphere** | The read-only-by-construction resource (no create/edit/delete/bulk on an operational log); status badge colouring by terminal state; filtering by status, category and provider; a stable idempotency key sent to the provider and the provider message id stored back; distinguishing "queued" from "sent"; separate timestamp columns per lifecycle event rather than one mutable status date. |
| **Must change** | (a) Melbourne Sphere dispatches through **BullMQ** with the existing transactional outbox — the HTTP request validates, commits, records and enqueues, and never waits on the provider. (b) Recipients must be **masked** in the list and detail views and protected behind permission; Logimart prints full addresses. (c) `delivered`, `bounced`, `complained`, `suppressed` are filter options in Logimart that **nothing ever sets** — there is no webhook ingestion at all. Melbourne Sphere must implement the signed Resend webhook, event-id idempotency, out-of-order tolerance and terminal-status precedence. (d) Manual resend does not exist in Logimart; Melbourne Sphere adds it with permission, confirmation, throttle, a new attempt row linked to the original, a new provider message id, and refusal for delivered/complained/suppressed recipients. (e) Retention: the table grows unbounded in Logimart. |
| **Do not copy** | Storing the raw exception message in `error` (leaks internal detail, potentially credentials, into an admin-readable column — Melbourne Sphere stores a classified safe failure code plus a redacted summary). Storing full `to`/`cc`/`bcc` and subject unconditionally. Deriving the provider from `app()->environment('production')` inside a logging service — provider selection belongs to validated configuration. Framework mail-event hooks are Laravel-specific; Melbourne Sphere's boundary is `packages/mail` plus the worker. |
| **Governing SRS** | MAIL 001–010 (new), ENQ 006, EVT 001–002, SEC 004, PRIV 001, NFR 005. |

## 3 Activity Log

| | |
| --- | --- |
| **Logimart behaviour** | Spatie Activitylog's `activity_log` table extended with audit-trail columns: `batch_uuid`, `log_name`, `description`, subject type/id, `event`, nullable morph `causer`, `attribute_changes` and `properties` JSON, `actor_type` (user/guest/system), `guest_name`/`guest_email`/`guest_phone`, `ip_address`, `user_agent`, `route`, `method`, `session_id`, with indexes on created_at, batch, actor type and guest email. The Filament resource is read-only (`canCreate`/`canEdit`/`canDelete`/`canDeleteAny` false). Retention is a weekly `activitylog:clean` scheduled command (default 365 days). A separate `login_histories` table (pruned at 90 days) keeps authentication events out of the general log. |
| **Suitable for Melbourne Sphere** | One consolidated, append-only activity surface that is read-only by construction; a batch identifier so one logical operation groups its events; actor typing (administrator / system / public visitor) rather than assuming a signed-in user; keeping specialised security records in their own store while surfacing them in one search experience; scheduled retention with a documented default. |
| **Must change** | Melbourne Sphere already has `audit_logs` and an authorization audit. The new Activity Log is a **read model over the existing records plus new operational events**, not a third parallel store — it must not lose the authorization-audit guarantees of RBAC 012. Event codes must come from a typed catalogue, not free-text `description`. Filters, pagination bounds and permission gating follow API 005/RBAC 006. |
| **Do not copy** | Plaintext `guest_email` / `guest_phone` / full `user_agent` columns on an append-only table with a 365-day retention — that is personal data accumulating outside PRIV 001's schedule. `session_id` stored alongside the event (a session identifier in a log an administrator can read is a session-fixation aid). Spatie's `properties` free-form JSON blob, which in practice invites whole request bodies into the log. |
| **Governing SRS** | ACT 001–006 (new), RBAC 012, PRIV 001–002, SEC 004. |

## 4 Security Settings

| | |
| --- | --- |
| **Logimart behaviour** | Four relevant groups. `AuthenticationSettings`: `login_enabled`, `remember_me_enabled`, `email_verification_required`, `default_login_method`, plus six *stored-but-unenforced* placeholders (`two_factor_enabled`, `passkeys_enabled`, `social_login_enabled`, `ldap_enabled`, `saml_enabled`, `azure_ad_enabled`). `PasswordPolicySettings`: min length, four composition toggles, reuse prevention with history count, expiry days, force change on first login. `LoginSecuritySettings`: max failed attempts, lockout minutes, throttling on/off, reset throttling on/off, notify user/admin, plus `recaptcha_enabled`/`turnstile_enabled` placeholders. `SessionSettings`: idle timeout, allow multiple sessions, force logout on password change, plus trusted-device placeholders. Password history has its own table (`user_password_histories`); sessions have `user_sessions`. |
| **Suitable for Melbourne Sphere** | The grouping itself (authentication / password policy / login security / session security) matches the requested navigation and is a good administrator mental model. Password history as a separate table. Force-logout-on-password-change. A per-administrator session list. Idle timeout as a validated bounded number. |
| **Must change** | Every setting must be **enforced by the existing auth stack** or must not exist. Melbourne Sphere's ranges are bounded by the SRS defaults (30 min idle / 12 h absolute, AUTH 002; 30 min reset token, AUTH 001; SEC 002 throttle ceilings) — a setting may narrow those, never widen them past the SRS bound without an SRS revision. Composition rules are not adopted as defaults: current guidance favours length plus breach screening, so composition toggles are omitted rather than shipped off. Changing policy must not invalidate existing hashes; the rule is "applies at next password change", documented explicitly. |
| **Do not copy** | **`login_enabled` as an administrator-editable boolean** — a single toggle that can lock every administrator out of the product with no recovery path; Melbourne Sphere refuses to expose it (SECS 007). **Placeholder settings that are stored but unenforced** (`two_factor_enabled`, `turnstile_enabled`, `ip_restriction_enabled`, …) — a security control that appears switched on but does nothing is worse than an absent control. **`throttling_enabled` / `reset_throttling_enabled` as UI switches** — brute-force protection is not administrator-disablable in Melbourne Sphere (SEC 002/003). `remember_me`, `email_verification_required`, `default_login_method` and the registration group are irrelevant: Melbourne Sphere has no public accounts (FUT 001) and one login method. |
| **Governing SRS** | SECS 001–008 (new), AUTH 001–003, SEC 002–004, RBAC 006/011–012. |

## 5 Cache Manager

| | |
| --- | --- |
| **Logimart behaviour** | `app/Filament/Pages/CacheManagerPage.php` shows cache driver, store, environment, framework/PHP version and whether config/route/view/event caches are warm. Header actions run artisan commands through a service: `cache:clear`, `view:clear`, `route:clear`, `config:clear`, `event:clear`, `optimize`, `optimize:clear`. Each action requires confirmation and names the artisan command it will run. |
| **Suitable for Melbourne Sphere** | An operational status panel (driver reachable, what is cached, last action and its result); confirmation dialogs that state plainly what will happen; grouping destructive actions apart from benign ones; showing the outcome of the last operation rather than a silent success. |
| **Must change** | Melbourne Sphere exposes a **registry of named cache namespaces and tags**, not framework internals: invalidate one registered namespace, invalidate one known resource/tag, warm approved caches. Redis availability and approximate entry counts per namespace replace "is the config cached". Operations are throttled, audited, non-blocking and fail safe while Redis is down. |
| **Do not copy** | **Executing shell/artisan commands from an admin HTTP request** — Melbourne Sphere never shells out from the admin API. **`cache:clear`, which flushes the entire cache store** — Melbourne Sphere's Redis also holds sessions, rate-limit counters and BullMQ state; a blanket flush would sign out every administrator and destroy queue and throttle state, which is exactly why `FLUSHALL`/`FLUSHDB`/pattern deletion/raw key access are prohibited (CMGR 004). **UI-only authorization**: `makeAction()` gates with Filament's `->disabled(...)`, but the `->action()` closure itself performs **no permission check**, so the capability rests on the button being greyed out — precisely the "hiding buttons is not authorization" failure RBAC 006 forbids. **`isSuperAdmin()` short-circuits** scattered through page classes instead of one resolver. |
| **Governing SRS** | CMGR 001–005 (new), CACHE 001–003, RBAC 006, SEC 001. |

## 6 Queue Monitor

| | |
| --- | --- |
| **Logimart behaviour** | `app/Filament/Pages/QueueMonitorPage.php` lists failed jobs from the `failed_jobs` table with a truncated reference, a job display name, connection, queue, failure time and a one-line exception summary. `FailedJobPayloadSummary` parses the payload JSON **for display only and never unserialises the queued command object**, degrading to null on malformed input. Retry is available per record and as a bulk action bounded by the administrator's own selection, each tallied independently; both are gated with Filament's `->authorize(...)` and require confirmation whose wording warns that retrying may repeat the operation. Queue depth per queue with oldest-age and a five-minute stall heuristic; a worker-liveness guess derived from stalled pending jobs. Page access requires `queue_monitor.view`; retry requires `queue_monitor.retry_failed_jobs`. |
| **Suitable for Melbourne Sphere** | This is the strongest module in the reference. Adopt: display-only payload summarisation that never deserialises a payload; bounded bulk retry over an explicit selection with per-item outcomes (`retried / not found / unsupported / failed`) rather than a single success toast; confirmation copy that states the operational risk of a repeat; separate view and retry permissions; showing the failed-jobs surface independently of the currently configured default connection; oldest-waiting age as the health signal. |
| **Must change** | Melbourne Sphere reads BullMQ's supported APIs — `waiting`, `active`, `delayed`, `completed`, `failed`, `paused` counts per registered queue — instead of SQL against a jobs table, and must be correct with **multiple worker replicas** (a stall heuristic derived from one process is not adequate; use queue metrics and worker heartbeats). Job detail must be redacted by an explicit allowlist (no reset tokens, CAPTCHA tokens, email bodies, API keys, auth headers or unnecessary personal data). Cancel/remove for eligible waiting or delayed jobs, and pause/resume for approved queues, are added; arbitrary job creation and payload editing are not. Every action is audited to the Activity Log. |
| **Do not copy** | The raw first line of an exception as the operator-visible summary (classify instead). `whereRaw('1 = 0')` as an empty-state device. Deriving worker liveness from a heuristic and presenting it as a boolean without saying it is an estimate. |
| **Governing SRS** | QMON 001–005 (new), EVT 002, MOD 002, RBAC 006, PRIV 001. |

## 7 Scheduled Tasks

| | |
| --- | --- |
| **Logimart behaviour** | Tasks are declared in code in `routes/console.php` (publish scheduled content every minute with `withoutOverlapping()`, daily prunes, weekly activity-log clean). `app/Filament/Pages/SchedulerMonitorPage.php` lists registered schedule events with their last run from `scheduler_histories` (pruned at 30 days) and offers "Run Now". `SchedulerService::runNow()` identifies the task by `sha1(command + cron expression)` matched against the framework's own registered events, so the identifier cannot name an unregistered command; it then regex-extracts the artisan sub-command and calls `Artisan::call()` **synchronously inside the web request**, capturing output. Access needs `scheduler_monitor.view`; running needs `scheduler_monitor.run`, checked inside the action body as well as on the button. |
| **Suitable for Melbourne Sphere** | Tasks registered in code and only *operated* from the UI; identifying a task by an opaque id resolved against the registry rather than accepting a command string; execution history as its own pruned table; last-run outcome and duration surfaced per task; "Run Now" as a confirmed, separately permissioned action; the checked-inside-the-action pattern used here (unlike the cache page). |
| **Must change** | Melbourne Sphere runs a "run now" as an **enqueued BullMQ job**, never inline in the HTTP request, and reports the outcome asynchronously. Recurring registration uses BullMQ job schedulers (`upsertJobScheduler`). A **distributed lock** must cover both the scheduled run and the manual run so multiple replicas and a manual trigger cannot overlap — `withoutOverlapping()` protects the scheduler path only, and Logimart's `runNow` can run concurrently with a scheduled execution. Missed-run policy, timeout, retry policy and next-expected-run must be explicit. Only allow-listed tasks may be run manually, and high-impact tasks require confirmation. |
| **Do not copy** | `Artisan::call()` on a string parsed out of a command with a regular expression — even allow-listed, string-parsed command execution is the wrong shape; Melbourne Sphere dispatches a typed task code to a registered handler. Synchronous execution inside an admin request. Any path that would let an administrator supply a cron expression, queue name, payload, shell command or SQL. |
| **Governing SRS** | TASK 001–006 (new), EVT 002, BLOG 004 (scheduled publishing), MOD 002, RBAC 006. |

## 8 FAQs

| | |
| --- | --- |
| **Logimart behaviour** | `faqs` (uuid, `faq_category_id`, question 500, `answer` longtext, `audience` JSON, `display_order`, `featured`, `status` default `draft`, `published_at`, `created_by`/`updated_by`, timestamps, soft deletes) with a separate `faq_categories` table and a `faq_service` pivot associating FAQs with services. Indexed on category, status, featured, published_at and display order. |
| **Suitable for Melbourne Sphere** | Category grouping, explicit display order, draft/published status with a publish timestamp, created-by/updated-by audit columns, and the index set (status + order + published_at) which matches the public query exactly. Associating an FAQ with a related entity (Logimart: services) is a good pattern if Melbourne Sphere later wants category-scoped FAQs. |
| **Must change** | Answers are rich content and must pass the **existing server-side sanitiser allowlist** (SEC 001) — the same path as posts and information pages, not a second one. Public reads are server-rendered and cached with tag invalidation on publish. `FAQPage` structured data is emitted only where the content and current search-engine policy permit it, consistent with SEO 004–006 and the existing `REVIEW_RICH_RESULTS` gate discipline. The `audience` concept does not apply (one public audience). Melbourne Sphere uses `expectedVersion` optimistic concurrency, which Logimart lacks. |
| **Do not copy** | Soft deletes as the deletion model for public content without a defined purge (Melbourne Sphere already uses explicit state transitions). `longText` answers with no maximum length. |
| **Governing SRS** | FAQ 001–005 (new), SEC 001, SEO 001/004, CACHE 001–002, NFR 006/011. |

## 9 Service Alerts

| | |
| --- | --- |
| **Logimart behaviour** | `service_alerts` (uuid, title 150, `message` text, `link_label`, `link_url`, `priority`, `starts_at`, `ends_at`, `is_active`, `display_order`, created/updated by, timestamps, soft deletes) with a composite index on `(is_active, starts_at, ends_at, priority)`. `ServiceAlertService::current()` selects **exactly one** alert — highest priority, then display order, then created-at as a deterministic tiebreak — cached for 60 seconds with a documented reason for caching plain attributes rather than a model. The bar renders above the header in both public layouts as `<aside role="status" aria-label="Service alert">` with an optional link that gets `rel="noopener noreferrer"` when the URL starts with `http` or `//`. |
| **Suitable for Melbourne Sphere** | The selection query and its composite index; a deterministic tiebreak so the displayed alert never flickers between requests; a short cache TTL justified by the time-sensitivity of the display window; rendering above the header in the layout; `rel="noopener noreferrer"` on external links. |
| **Must change** | Melbourne Sphere needs **severity/type** (informational, warning, emergency) with accessible semantics chosen by severity — `role="status"` for informational, an assertive treatment reserved for genuine emergencies — not one fixed `role="status"`. **Dismissal** is required and must be keyboard accessible, must persist per viewer, and must be **version-aware** so an edited alert reappears. Multiple concurrent alerts need the defined priority rule rather than a hard limit of one. Display windows are evaluated in **Australia/Melbourne** deliberately (NFR 012) while instants are stored in UTC. Layout must reserve space so the bar does not shift content (NFR 001 CLS). Contrast must hold at emergency severity (NFR 006). |
| **Do not copy** | `str_starts_with($url, 'http')` as URL validation — Melbourne Sphere validates the URL server-side against an allowlisted scheme set and treats internal links as validated routes; `javascript:`, `data:` and protocol-relative URLs are rejected at write time, not patched at render time. Unbounded `text` message with no length limit. |
| **Governing SRS** | ALRT 001–007 (new), SEC 001, NFR 001/006/011/012, CACHE 001–002. |

## 10 Testimonials

| | |
| --- | --- |
| **Logimart behaviour** | `testimonials` (uuid, `customer_name`, `company`, `designation`, `testimonial` text, optional `rating`, `approved` default false, `active`, `featured`, `display_order`, created/updated by, timestamps, soft deletes) indexed on approved/active/featured/order. Publication requires `approved` to have been set explicitly. |

An optional portrait must come from the existing approved-media pipeline (MED 001–004) with alt text. Quote length is bounded and sanitised. An optional link to a directory listing uses the existing relation rather than a free-text company string where a listing exists. Rating is omitted: Melbourne Sphere already has a real, moderated review system and a second unmoderated star display would misrepresent it. |
| **Do not copy** | Publishing on a bare boolean with no recorded approver. Inventing testimonial content to populate a homepage — the SRS forbids sample content in production (CFG 002) and this module must ship empty until the client supplies consented quotes. |

## 11 Clients / partner logos

| | |
| --- | --- |
| **Logimart behaviour** | `clients` was originally exactly the partner-logo concept — name, `website_url`, `active`, `featured`, `display_order`, created/updated by, soft deletes — and was **later overloaded** into a B2B customer account (`add_business_account_fields_to_clients_table`, `client_user`, `client_carriers`, `client_id` on shipments, non-expiring API tokens). The public-facing logo strip and the customer-account entity now share one table and one admin resource. |
| **Suitable for Melbourne Sphere** | The original shape only: organisation name, website URL, active/featured, display order, audit columns, and the index set. |
| **Must change** | Melbourne Sphere's Clients module is **public marketing content and nothing else** — it is not an account, not an identity, and grants no access. That boundary is explicit in the requirement so the Logimart drift cannot repeat here (FUT 001 already excludes business-owner accounts). The logo is an approved media asset with mandatory accessible alt text; the website URL is validated and rendered with safe external-link attributes; a relationship label describes the association honestly. The public section must look deliberate when nothing is published rather than rendering an empty strip. |
| **Do not copy** | The overloading itself — the single clearest architectural lesson in the reference. Displaying an organisation's logo without recorded authorisation. |
| **Governing SRS** | PTNR 001–005 (new), MED 001–004, SEC 001, FUT 001–002. |

## 12 Admin navigation and shared UX patterns

Logimart groups these modules under a **"System & Settings"** navigation group with numeric `navigationSort` (Email Logs 20, Scheduler 50, Queue Monitor 60), a failed-job **count badge** in danger colour on the Queue Monitor, breadcrumbs that name the group, and a page subheading that states what the screen is for in one sentence. Operational pages are `Page` classes rather than CRUD resources; operational records are `Resource` classes with create/edit/delete disabled. Navigation registration is tied to the same predicate as access (`shouldRegisterNavigation() === canAccess()`).

All of this transfers to Melbourne Sphere's Refine shell, which already has grouped navigation (Overview / Directory / Editorial / Community / Configuration) and an `accessControlProvider` fed by server-calculated effective permissions. The new modules extend the existing groups — a **System** group for the five operational screens, **Configuration → Security** for the four security-settings screens, and **Website** for the four content modules — with the existing route→permission mapping and the existing waiting/forbidden states (RBAC 010). Melbourne Sphere's navigation predicate is already the server's effective permission set, which is the correct version of Logimart's pattern.

## 13 Security weaknesses and Laravel-specific patterns that must not be copied

Consolidated register. Each item is a concrete observation, not a general caution.

| # | Observation (path) | Why it must not be copied | Melbourne Sphere control |
| --- | --- | --- | --- |
| W1 | Cache Manager actions gate on `->disabled(...)` only; the `->action()` closure runs with no permission check (`app/Filament/Pages/CacheManagerPage.php:210–217`) | Authorization that exists only in the rendered button; a direct component call would bypass it | Backend `@RequirePermissions` on every route plus the service-layer check (RBAC 006) |
| W2 | Admin UI executes artisan/shell commands (`CacheManagerPage`, `SchedulerService::runNow`) | Command execution from an HTTP admin surface is an escalation path and blocks the request | Typed task codes dispatched to registered handlers via BullMQ; no shell (CMGR 004, TASK 003) |
| W3 | `cache:clear` flushes the whole cache store | Melbourne Sphere's Redis also holds sessions, throttle counters and queue state | Registered namespaces/tags only; `FLUSHALL`/`FLUSHDB`/pattern deletion prohibited (CMGR 004) |
| W4 | SMTP password stored in the settings table and editable in a browser form (`app/Settings/MailSettings.php`) | A credential in application data, reachable by anyone with settings access | Secrets stay in environment-managed configuration; never in settings, never in an API response (SEC 004, SET 004) |
| W5 | `login_enabled` toggle (`app/Settings/AuthenticationSettings.php`) | One switch can lock every administrator out with no recovery path | Refused: no setting may remove the last secure recovery path (SECS 007) |
| W6 | Placeholder security settings stored but unenforced (`two_factor_enabled`, `turnstile_enabled`, `ip_restriction_enabled`, `suspicious_login_detection`, …) | A control that appears enabled but does nothing is a false assurance to the operator | Only enforced settings exist; a setting ships with its enforcement or not at all (SECS 001) |
| W7 | `throttling_enabled` / `reset_throttling_enabled` as administrator switches | Brute-force protection becomes optional | Not administrator-disablable; bounds may narrow, never remove (SECS 004, SEC 002/003) |
| W8 | `guest_email`, `guest_phone`, `session_id`, full `user_agent` on `activity_log` with 365-day retention | Personal data accumulating outside the retention schedule; a session id readable by administrators | Typed events, redaction, retention rows added to PRIV 001 (ACT 004–006) |
| W9 | Raw exception text in `email_logs.error` and as the operator-visible failure summary | Leaks internal detail into an admin-readable column | Classified failure code plus redacted summary (MAIL 006) |
| W10 | Full `to`/`cc`/`bcc` and subject stored and displayed unconditionally | Recipient addresses are private contact data (ENQ 005, PRIV 001) | Masked by default, full value permission-gated, retention-bounded (MAIL 005) |
| W11 | Terminal statuses (`delivered`, `bounced`, `complained`, `suppressed`) offered as filters with nothing that sets them | An operator reading "no bounces" concludes something the data cannot support | Webhook ingestion is part of the same requirement as the status vocabulary (MAIL 007–008) |
| W12 | `str_starts_with($url, 'http')` as the external-link test (`service-alert-bar.blade.php`) | Render-time string sniffing is not URL validation; `javascript:` and `data:` are not excluded at write time | Server-side scheme allowlist at write time (ALRT 005, SEC 001) |
| W13 | `isSuperAdmin()` short-circuit repeated in page classes | Authorization logic duplicated across surfaces, diverging from the resolver | One server-side resolver; no component recreates it (RBAC 005) |
| W14 | `clients` overloaded from marketing logos into customer accounts with API tokens | Public content and identity in one table and one screen | Partner logos are content only and grant no access (PTNR 001, FUT 001) |
| W15 | Framework-coupled patterns generally: Spatie Settings property bags, Eloquent model events for mail logging, Filament `canAccess()` statics, artisan-based operations, soft deletes as the universal delete | Laravel-specific architecture that would fight NestJS module boundaries and the existing envelope/permission/audit contracts | Melbourne Sphere reproduces the *behaviour* through its own modules, DTO allowlists, guards and Prisma migrations (ARC 001–005, MOD 001–002) |

## 14 What Melbourne Sphere gains that Logimart does not have

Recorded so the reference is not mistaken for a target: `expectedVersion` optimistic concurrency on every mutation, transactional audit committed with the change, a default-deny guard chain with a typed permission catalogue, effective-permission caching with authorization-version invalidation, a durable outbox with a dispatcher, Turnstile-gated public writes, field encryption for private contact data, verified-TLS database connectivity in production, real MySQL integration tests, and Playwright UAT journeys.
